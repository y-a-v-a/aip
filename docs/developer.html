1. Principles

  • KISS. Plain PHP 8 + the bundled cURL extension. No framework, no Composer, no database, no front-end build. A page is a PHP file.
  • Runs on cheap shared hosting. Everything must work on an Apache host with only .htaccess — no daemons, no cron, no mail setup.
  • Files are the database. JSON / text files under data/, written with locks.
  • Secrets are never stored in plain form. PINs are bcrypt, login-link and device tokens are sha256, the API key is never in the code.

4. Anatomy of a page

Every page follows the same pattern — no router abstraction, no templates engine:

<?php
require_once __DIR__ . '/auth.php';   // starts the session, loads config + lib/users
require_login();                      // or require_admin() — redirects / 404s and exits
require_once __DIR__ . '/lib/view.php';

$error = '';
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    if (!csrf_check($_POST['csrf'] ?? null)) {
        $error = 'Session expired, please try again.';
    } else {
        // … do the work …
    }
}

$token = csrf_token();
page_top('Title');                    // header, nav, inline CSS
?>
<form method="post"><input type="hidden" name="csrf" value="<?= e($token) ?>"> … </form>
<?php
page_bottom();

Adding a page? Also add it to the $pages whitelist in router.php, or php -S (Docker, e2e) answers 404. Apache needs nothing extra. Escape all output with e(), and put a CSRF token in every POST form.

5. Recipe generation

  • The pantry is appended to the system prompt as “AVAILABLE INGREDIENTS (the ONLY ones you may use)” and shuffled each call to avoid positional bias.
  • Without a note, pick_feature() chooses a random ingredient matching PROTEIN_KEYWORDS (lunch/dinner) or FRUIT_KEYWORDS (dessert) as the dish’s centre.
  • The request asks OpenRouter for usage.include, so the exact USD cost lands in api_log.jsonl (metadata only — never recipe text).
  • To swap the provider, only generate_recipe() needs to change.

6. Authentication

Identifiers

A user is keyed in users.json by an identifier from normalize_identifier(): input containing @ must be a valid email and is lowercased; anything else must look like a phone number and is reduced to an optional leading + plus digits (≥ 6 digits). The admin page additionally requires phones to start with +, so WhatsApp links work and 06… / +316… can’t become two users.

How a request is recognised

Login links

  • Tokens are 24 random bytes (48 hex chars). Only sha256(token) is stored; lookups use hash_equals(). Redemption happens inside the users_update() lock, so a link can’t be used twice concurrently.
  • Constants in lib/users.php: INVITE_TTL_SECS (7 days), REMEMBER_TTL_SECS (1 year), MAX_DEVICES (10, oldest dropped).
  • The device cookie aip_device is HttpOnly, SameSite=Lax, path /, and Secure on HTTPS (same rule as the session cookie via REQUEST_IS_HTTPS).
  • Sign out everywhere empties devices, drops the invite and sets revoked_at = microtime(true); sessions store their start time in $_SESSION['at'], and any session older than revoked_at is rejected.
  • PIN login (attempt_login()) also issues a device token when “Keep me signed in” is ticked.

Admin gate

require_admin() = require_login() + "admin": true on the current user (else HTTP 404, so the page isn’t advertised). admin.php then demands a PIN step-up: confirm_admin_pin() sets $_SESSION['admin_ok'], and admin_confirmed() accepts it for ADMIN_CONFIRM_SECS (1800 s), sliding on each view. The flag can only be set by tools/make_user.php --admin.

Lockout and CSRF

MAX_FAILED (5) bad PINs for one identifier within LOCKOUT_SECS (300 s) lock it; state is in data/lockout.json and shared by the login form and the admin PIN step-up. Every POST carries a per-session CSRF token checked with hash_equals().

Always modify it through users_update(fn(array &$users) { … }): it opens the file with flock(LOCK_EX), hands you the decoded array, and writes it back — so web requests and CLI tools never clobber each other.

9. Running locally

# key from your shell or a .env file beside docker-compose.yml
OPENROUTER_API_KEY="sk-or-..." docker compose up -d
open http://localhost:8000          # log in as +31644444444 / 123456 (admin)

docker compose exec -T aip php -l /app/admin.php          # lint (no PHP on the host needed)
docker compose exec aip php tools/list_users.php          # CLI inside the container
docker compose logs aip

PHP/TXT edits show up after a second or two (bind mount). Only Dockerfile or docker-entrypoint.sh changes need docker compose up -d --build. Without Docker: php -S localhost:8000 router.php after php tools/make_user.php <id> <pin> --admin.

11. Deploying

  1. Upload the repo (minus e2e/, Docker files, docs if you like) to the subdomain’s document root — the app expects to live at /.
  2. Make data/ writable by PHP (chmod 775 data). The web app now writes users.json too.
  3. Provide the API key via data/api_key (recommended) or SetEnv.
  4. Create the admin over SSH: php tools/make_user.php <id> <pin> --admin.
  5. Verify /data/users.json, /data/api_key, /lib/openrouter.php, /ingredients.txt return 403/404.

Never sync into data/ on the host: it holds users added on the web, sessions’ device hashes, recipes and the cost log. If you automate deploys with rsync --delete, exclude data/ (except data/.htaccess).

12. Security checklist

  • Escape output with e(); never echo request data raw.
  • CSRF token on every state-changing POST; no state changes on GET (except logout).
  • New entry point → add it to router.php; new private directory → give it a deny-all .htaccess.
  • File names from user input: whitelist-regex them (see get_recipe()).
  • Store secrets hashed; compare with hash_equals() / password_verify().
  • Change users.json only through users_update().
  • Admin-only features: require_admin() and check admin_confirmed() before acting.
  • Known limits: lockout is per identifier (not per IP); a login link is a bearer credential until used; no proof of phone/email ownership — the admin vouches.
